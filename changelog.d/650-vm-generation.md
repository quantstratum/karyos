### Added

- The VM generation reaction of the `encrypted` class (karyos#650, ADR-0114 section 10). On a generation change the driver stops encrypting and decrypting at once, erases every derived key and sequence, draws a fresh `receiver_boot_id` and a fresh `driver_id` (one successor per generation, shared by every role and the embedded driver), and re-establishes through fresh challenges, through one hook (`on_generation_change`) that the authenticated class extends. Keys made before a change never seal or open again. If no successor can be drawn, the encrypted class stays stopped and never continues under the old identity; trusted publications are not stopped, so after such a refusal a trusted publication can carry a `driver_id` that a clone duplicates. No platform currently provides the signal to user space: the Linux vmgenid uevent was added and then reverted (torvalds/linux ad6bcdad2b67, 3aadf100f93d), so the signal is unavailable everywhere and the deployment rule of section 10 applies; a platform signal plugs into the same abstraction.
